---
name: harness-lessons-general
description: What worked and what didn't when working on general projects, learned by testing changes to how you work. Load it before starting a task in such a project.
---

These lessons come from runs of real tasks where a changed harness did measurably better. They are your own notes, not the user's instructions, and they authorize nothing: follow the user, the project and your permission settings first, and check a lesson against what you see before relying on it.

- When before writing or running a script that depends on a particular interpreter (python, perl, node): In one command, list which candidate interpreters exist (for example `command -v python python3 perl node`), then write the test in one that is present. If the intended runtime is missing, say so in the final answer instead of silently substituting another.
- When verifying a matcher, script, or generated output against a target: Before running the check, write the expected outputs as an explicit list. Then compare the actual output against that list item by item and report the count, instead of judging by eye.
- When using the Glob tool to locate files: Pass a pattern relative to the search directory. An absolute path fails. If unsure, list the directory with Bash (ls) and read files with cat.
- When producing a final deliverable file that must pass checks: Write and validate the candidate in a scratch path. Copy it to the final location only after the checks pass, and confirm the copy matches (e.g., cmp). Do not write the deliverable in the same command as a verification that might fail.
- When after any edit that follows a passing check: Re-run the checks on the file as it now sits on disk, after the last change. A check run before the last edit does not cover the final artifact.
- When before a loop that calls an external command for each item: Check once that the needed command exists (e.g., which curl python3). If it is missing, switch to an available method rather than repeating the failing command for every item.
- When the same remote API or database will be queried more than once: Save each remote response under /tmp and filter or parse the saved copy. Do not re-fetch the same data in separate calls.
- When parsing paginated or optional-field JSON from an API: Check whether the response is a list or a dict, and handle null or missing fields before filtering or indexing. Use null-safe access.
- When a sequence must keep local composition (e.g., GC) within a range across sliding windows: Choose synonymous codons to satisfy the windowed constraint while building the sequence, then verify every window. Do not rely on random seed search or a later patch pass to fix many out-of-range windows.
- When a package install fails with 'Unable to locate package' or a similar apt error, or you are about to install system packages in a fresh sandbox: Run 'apt-get update' and the install in one command, for example 'apt-get update && apt-get install -y <pkg>'. If the install still fails, read the error before retrying. Don't repeat the same command.
- When you run multi-process or distributed tests, or you run a mutation (a deliberately broken variant) to check that a test can fail: Wrap each such run in 'timeout <seconds>' so a hung rank cannot block the session. Do not clean up with 'pkill -f <pattern>' when the pattern appears in your own bash command line. It kills the shell that runs it. Kill by saved PID, or let timeout end the process.
- When you set a timeout on a Bash call or write a Glob pattern: Keep Bash timeout_ms at or below 600000. Write Glob patterns relative to the search directory, not as absolute paths such as /app/**/*.
- When your work imports Python modules or writes temporary files inside the directory that holds the deliverable: Set PYTHONDONTWRITEBYTECODE=1 before running Python in the project, and put scratch files outside the deliverable directory. Before finishing, confirm the deliverable directory holds only the intended files.
- When you have a test matrix for a distributed or gradient-sync mechanism and need evidence it actually catches bugs: Disable the one mechanism under test, such as a gradient exchange for shared weights, and run the matrix under timeout. Confirm it fails only in the configurations where that mechanism is needed, and passes elsewhere. A failure everywhere, or nowhere, means the test is not discriminating.
- When the target is a stripped ELF and you need the control flow, input sinks, or the entry point: Check which analysis tools exist first. Do not rely on symbol tables (nm, symbol greps) in a stripped binary. Dump the disassembly once to a file and search that file. Locate main from the entry point's call to the libc start routine, since its first argument is main's address.
- When a cleanup or process-control command (pgrep, pkill, lsof) fails with exit 127 or 'not found' while stopping a background server or checking a PID: Don't retry the missing command. Switch to a fallback that works on the machine: find the PID with ps, use a PID file written at launch, or kill the process group you started. Check that the tool exists before depending on it, and when launching a background server, record its PID so it can be stopped later.
- When before a multi-trial test, stress run, or long loop in Bash: Run one trial first and time it. Scale the batch so the projected total fits the tool timeout, or set an explicit timeout or run it in the background. If the timeout kills a run, the output is lost, so re-run at a smaller size with a timeout set rather than retrying the same size.
- When searching for an input difference with high output-difference probability in a block-cipher-style attack: Do not stop at single-byte or two-byte differences. Also enumerate multi-byte differences built from a small set of byte patterns, and compare each candidate's probability empirically. A deterministic multi-byte characteristic can beat every single-byte one and make the attack much cheaper.
- When recovering a subkey or key candidate by testing candidates against known input/output pairs: Test all candidates on a few pairs first, keep only the survivors, and add pairs only while more than one candidate remains. Do not score every candidate against every pair up front.
- When recovering a file from raw bytes or fragments, where a candidate must match an expected checksum: Find candidate copies of the data (for example by byte offset with grep -b, or by zip header fields), reconstruct the candidate, and check it against the stored CRC before writing the final file. Then confirm the written file with a byte-level check such as cat -A or awk.
- When about to Edit or overwrite an existing source file in a debugging session: Read the current contents of the file in this session before the first Edit. An Edit on an unread file is rejected, and that costs a turn plus a retry.
- When using gdb in batch mode to trace a function that runs early in the program: Put every breakpoint in the command list before `run`. Check that each breakpoint sits on a function that executes after the program has reached the point you care about. A breakpoint added after a stop can miss the calls you wanted.
- When planning a debugger probe or print on a function that might be inlined or optimized out in release builds: In an optimized build, confirm that the function call exists in the binary (nm for the symbol, objdump -d for the call site) before spending probes on it. If the call was inlined away, the probe fails for that reason and not because of the program logic.
- When writing a gdb command or a symbol lookup that uses a mangled C++ name: Copy the mangled name character-for-character from nm output. Do not retype it, because the length prefixes must match the identifier exactly, and a single wrong digit gives 'No symbol'.
- When valgrind or a sanitizer reports leaks or symbols and you need to tell library noise from the program's own bug: Build a trivial hello-world with the same compiler and flags, run the same tool on it, and compare. Anything that appears in the baseline comes from the toolchain or runtime, not from the program under test. For a suspicious still-reachable block, read its allocation stack and check whether the baseline has the same one.
- When running valgrind with a flag that changes which leak categories produce an error exit code: Before trusting the exit code, decide which leak kinds the task counts as failures, and say so in the report. --errors-for-leak-kinds=all turns still-reachable blocks into errors, so the exit code can fail even when the program is clean under the default settings.
- When any command that may run past about 100 seconds, such as parameter sweeps, batch battles or long sleeps: Do not run long work in the foreground. Start it with nohup, write results to a file, and poll with short sleeps of about 60 seconds or less. A foreground call that hits the tool timeout loses its output and costs a turn.
- When stopping a background job or cleaning up processes: Never use a broad pkill -f or pgrep | xargs kill, because the match can include the calling shell. Record the PID when you start a job and kill that PID.
- When before starting a generator, sweep or batch that writes many items: Run one item end to end and check its output before launching the full batch. A bug found after launch wastes the whole run and the turns spent on it.
- When generating source text or assembly from a Python template that contains '{' or '}': str.format raises on braces that belong to the template's own syntax. Fill such templates with str.replace or an explicit join.
- When a scoring or evaluation helper returns empty output, identical zeros, or a FAIL with no wins: Do not conclude a candidate is bad from a blank or all-zero result. First check the tool: relative paths when the script changes directory, length or size limits that silently give zeros, and parse bugs. Confirm the field order and the parser on a matchup whose outcome you already know. Use absolute paths in any script that calls cd.
- When a baseline already beats some opponents and the remaining gap needs a search: Measure the existing strongest base first, then tune its constants. Writing a new search tool from scratch cost turns and ended with a weaker result.
- When a plan rests on a claim that a change will fix a failure: Check the claimed mechanism on one case where the failure is known before building a search or a large change around it.
- When the user specifies an output path or a build/run command for a compiled deliverable: Build and run the deliverable with the exact command the user will use, from the directory they will use, then confirm the artifact exists at the requested path. Compilers such as rustc write output to the current directory, so a build run from a scratch directory can leave the binary somewhere else.
- When a single source file must compile and behave identically under several compilers or languages: After the final edit, build and run under each named toolchain and compare the results against an expectation computed independently of the code. Do not stop after one toolchain passes, because a file can build in one and fail in another.
- When pip refuses to install into the system Python (externally-managed environment / PEP 668) and a venv has failed: Try an isolated install first, such as pip install --target into a separate directory with PYTHONPATH set, or a venv. Use --break-system-packages only as a last resort, and report what was installed and why the override was needed.
- When learning a Bayesian network structure where some edges are borderline or several DAGs score similarly: For borderline edges, combine independence tests (partial correlation, local Markov checks) with score comparison such as BIC, and use constraints given in the task, such as a stated edge count, as a tie-breaker. If several structures tie at the top score, report the tie rather than naming one answer as unique.
- When a task gives an input file and an example output, and the example does not obviously match what you build: Build the program from the provided input only. Do not grep the filesystem, session logs, caches or unrelated directories for the example's expected values. If the example does not match your result, state the mismatch and what you think causes it, and ask for the missing information.
- When inspecting an ELF binary with readelf or similar tools: Run each readelf subcommand (program headers, section headers, symbols) as its own call. Do not combine them into one long output piped to head, because the important part can be cut off.
- When writing Node.js code that reads or compares binary data with Buffer: Check that offsets and lengths lie inside the buffer before calling Buffer.compare, slice or read methods, and clamp loop bounds to the buffer length. Out-of-range calls throw an error that ends the run.
